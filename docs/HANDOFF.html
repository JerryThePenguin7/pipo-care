1. Executive Summary

Pipo Care is a web application that protects users from digital eye strain and dryness while they use screens. During a monitoring session, the app uses the device camera and an on-device computer-vision pipeline (Google MediaPipe Face Landmarker) to count the user's blinks in real time and compute a blink rate per minute. When the blink rate falls below 7 blinks/minute (a recognized dry-eye risk indicator), a full-screen alert opens and only clears once the app has counted five real blinks. Every session is stored on a small Node.js backend so users can review history, per-session detail, and trend charts.

The product is a working prototype: all core features run end-to-end (camera capture, blink detection on desktop and mobile, dryness alerts, persistence, history, insights, settings with dark mode). It is currently deployed nowhere — it runs locally and over the local network for demos. Video frames never leave the device; only numeric session statistics are sent to the backend.

4. Architecture & Data Flow

4.1 Runtime topology

  • Development: two processes via npm run dev — Vite dev server (https://localhost:5173, also on LAN) and Express API (http://localhost:3001). Vite proxies /api/* to Express, so the browser only talks to one origin.
  • Production mode: single process — Express serves the built SPA from client/dist and the API on the same port (3001) when NODE_ENV=production.

4.2 A monitoring session, end to end

  1. User taps Start capture on the Monitor page. cameraPrereqMessage() verifies the page is a secure context (HTTPS/localhost) before requesting the camera (1280×720@30 ideal, front camera).
  2. useBlinkTracker.start(video) begins a requestAnimationFrame loop. Each frame is passed to MediaPipe FaceLandmarker.detectForVideo() with a monotonically increasing timestamp derived from video.currentTime (important for mobile correctness).
  3. For each frame the hook computes the Eye Aspect Ratio (EAR) per eye from 6 landmarks, plus MediaPipe blendshape blink scores. A blink is a transition closed → open in a hysteresis state machine (see §5).
  4. Live stats: rolling blinks-in-last-60s (displayed as blinks/min), session average, total count. A SamplePoint snapshot is appended every ~5 seconds.
  5. If the rolling rate stays < 7/min for ~7 s (logic in Monitor.tsx), the full-screen DrynessModal opens (plus optional browser notification). Acknowledging suppresses re-alerts for 50 s.
  6. On Stop, the tracker returns a snapshot, and the page POSTs the complete SessionRecord to /api/sessions.

4.3 Data model (SessionRecord)

{
  id: string (uuid, server-generated),
  startedAt / endedAt: epoch ms,      durationMs: number,
  blinkCount: number,                 avgBlinksPerMin: number,
  minBpm / maxBpm: number | null,     alertsTriggered: number,
  status: "healthy" | "medium" | "slightly_dry" | "dry",
  samples: [{ t: seconds, bpm, cumBlinks, avgEar, status }, ...],   // one per ~5s
  notes: string,                      createdAt: epoch ms
}

Status thresholds (in client/src/types.ts → statusFromBpm): ≥15 healthy · ≥10 medium · ≥7 slightly_dry · <7 dry.

5. The Blink-Detection Pipeline (most important code)

Everything lives in client/src/hooks/useBlinkTracker.ts. Read this file first.

  • Model: MediaPipe Face Landmarker (face_landmarker.task, float16) + WASM, both loaded from CDN at runtime. Delegate selection: CPU first on mobile user agents (mobile WebGL proved unstable), GPU first on desktop, with fallback either way.
  • EAR (Eye Aspect Ratio): classic 6-landmark formula per eye — (‖p2−p6‖ + ‖p3−p4‖) / (2·‖p1−p4‖). Landmark indices: left [362,385,387,263,373,380], right [33,160,158,133,153,144]. Lower EAR = more closed.
  • Adaptive baseline (critical): absolute EAR varies hugely by device, face and distance (one tester's open eyes sat at ~0.15–0.18 while blinks hit ~0.01). Therefore the hook keeps an exponentially smoothed "eyes-open" baseline (baselineEarRef, factor 0.88/0.12, updated only while eyes look open) and detects blinks relative to it: closed when min(earL, earR) < 0.5 × baseline or blendshape blink score > 0.54; open again when EAR recovers toward baseline (several OR'd conditions, because blendshapes lag on phones). Do not replace this with fixed EAR thresholds — that exact bug already happened once and broke mobile counting entirely.
  • Debounce: blinks ignored in the first 350 ms of a session and within 100 ms of the previous blink.
  • Timestamps: detectForVideo must get strictly increasing timestamps; the hook derives them from video.currentTime and clamps with lastMpTsRef.

5b. The Dry-Eye Analysis Engine (home page)

The home page leads with an AI dry-eye analysis card instead of the old 7-day status list. The scoring lives entirely in server/analysis.js (pure functions, no I/O) and is served by GET /api/analysis; client/src/components/AiAnalysisCard.tsx only renders the verdict. Unit tests: server/analysis.test.mjs, run with npm test --prefix server.

It is a deterministic, explainable rule model — not a trained classifier. With a few hundred samples from a handful of devices there is nothing to fit, and the user needs to see why the number moved. Each factor produces a 0-1 sub-score; the final 0-100 risk index is the weighted mean of the factors that had enough data, so unavailable factors drop out and the rest are re-normalised.

FactorWeightWhat it measures
Average blink rate34%Duration-weighted mean blinks/min. ≥15 healthy, <7 is the dryness threshold
Time in the dryness band22%Share of monitored time under 7 (and under 10) blinks/min
Blink-free staring gaps18Longest stretch with no blink, plus rate of gaps over 10 s
Symptoms you reported14Onboarding scales: discomfort, strain, reliance on relief, screen exposure
Repeat dryness alerts10Alerts beyond the first per 10 minutes of monitoring
Blink decay during sessions10Least-squares slope of blink rate across a session (fatigue curve)
Trend vs earlier sessions6Recent half of the window against the earlier half

Weights are relative, not percentages — the score is the weighted mean over whichever factors had data. The self-report factor deliberately sits below the measured blink rate: symptoms are the half of dry eye a camera cannot see, but self-reports drift while the measurements move day to day. When symptoms are high and the measured blink rate is fine, the engine says so — that pattern points at evaporation or tear quality rather than blink frequency, and is the most clinically useful thing this model produces.

Bands: <20 Low · <40 Mild · <65 Moderate · ≥65 High. Confidence comes from session count and total monitored minutes.

Three quirks of the stored data drive the guard rails — read these before touching the weights.
  1. SamplePoint.bpm counts blinks in the trailing 60 s, so every sample before t = 60 s reads low by construction. Exposure and decay factors skip them.
  2. avgBlinksPerMin is blinkCount / elapsed minutes — unbiased at any duration — so it carries the heaviest weight.
  3. Because of (1), almost every session logs one dryness alert in its first minute. Only excess alerts on sessions ≥ 90 s count.

Captures under 15 s or with fewer than 3 samples are discarded as noise (the store already contains several 0-3 s aborted captures); the card reports how many were skipped. If the window holds no usable session the engine falls back to the most recent usable captures, and if there are none at all it returns an insufficient_data state with a "run a capture" call to action.

5c. Accounts, Sign-in and Onboarding

5c.1 How sign-in works

  1. Login.tsx fetches /api/auth/config, loads Google Identity Services from Google's CDN (with ?hl=en so the button matches the English UI) and renders the official button. No client ID configured → the page explains how to create one instead of failing silently.
  2. Google returns an ID token in the callback. The browser POSTs it to /api/auth/google.
  3. auth.js → verifyGoogleIdToken() validates it with google-auth-library (signature, expiry, and audience = our client ID). Nothing the browser claims is trusted; the Google credential itself is never stored.
  4. The server upserts the account (keyed on Google's sub) and sets pipo_session: HttpOnly, SameSite=Lax, Secure only over HTTPS, 30 days, value = base64url(payload).HMAC-SHA256 verified with timingSafeEqual.
The dev login is a seam, not a back door. POST /api/auth/dev-login answers 404 unless PIPO_ALLOW_DEV_LOGIN=1 and NODE_ENV !== "production". It exists so the app can be demoed without a Google Cloud project. Keep both conditions if you touch that code.

5c.2 Onboarding

Three steps in Onboarding.tsx — profile (name + photo), appearance (light/dark, previewed live), and four 1-5 statements plus a primary reason. The wording lives server-side in onboarding.js and is fetched via GET /api/onboarding/schema, so the questions, their validation and the scoring all read from one definition. RequireAccount in App.tsx keeps unfinished accounts on /welcome; Settings links back with ?redo=1 to edit the answers later.

Avatars are cropped square and downscaled to 256 px JPEG in the browser (lib/avatar.ts) before upload — they are stored as data URLs inside users.json, so unbounded images would bloat the store. The server additionally rejects anything that is not an https URL or an image data URL, and caps it at 2 MB.

5c.3 Existing history

Sessions recorded before accounts existed have no userId. claimLegacySessions() gives them to the first account created on an install, so an upgraded folder keeps its history. Every later account starts empty. This runs once and is invisible afterwards — if you are testing sign-in against real data, remember that creating a throwaway account first will consume that migration.

5e. The Dryness Alert

Lifecycle lives in Monitor.tsx; DrynessModal.tsx is presentational. Constants at the top of Monitor: BLINKS_TO_CLEAR 5, REMINDER_MS 8s, SUPPRESS_MS 50s, LOW_FOR_MS 7s.

  1. Rolling rate under 7/min for LOW_FOR_MS → openDryness(). It records alertBaselineRef = blinkCount, chimes, fires the notification and starts the reminder interval.
  2. An effect on tracker.blinkCount computes blinkCount − baseline and clears the alert at BLINKS_TO_CLEAR. There is no acknowledge button — blinking is the only normal way out, which is the whole point of the mechanic.
  3. While the alert is open and document.hidden, the interval re-fires the notification (same tag + renotify so it replaces rather than stacks, requireInteraction so it persists) with a chime, showing live progress. Returning to the tab closes the OS notification and lets the modal take over.
Audio must be unlocked by a gesture. unlockAlertSound() is called from the Start capture click. Chimes fire minutes later with no gesture anywhere near them, and a cold AudioContext is blocked by autoplay policy. The chime itself is synthesised (lib/alertSound.ts) — no asset, works offline. Users can mute it in Settings.
Background detection is best-effort. useBlinkTracker.schedule() falls back from requestAnimationFrame (which never fires in a hidden tab) to a 200 ms timer, so the pipeline survives being backgrounded — verified: ~55 fps via rAF when visible, timer-driven when hidden, rAF again on return. But browsers clamp hidden-tab timers to about 1 Hz, far below what a 100-400 ms blink needs, so blinks may not register until the tab is visible again. The alert keeps nagging rather than clearing early, which is the failure mode you want. True full-rate background counting needs frames pulled off the MediaStreamTrack (MediaStreamTrackProcessor, Chromium-only) or an AudioWorklet clock, rather than reading the <video> element from a throttled timer.

A dismiss link appears after 20 s (ESCAPE_AFTER_MS in the modal). Do not remove it: the overlay covers the Stop button, so without it a user whose face has left the frame is trapped with no way to end the session.

Note alertsTriggered now counts alerts fired rather than alerts acknowledged, which is what the field name always implied and what analysis.js's alert-burden factor assumes.

5f.1 How the sharing works

Monitor, History, SessionDetail, Insights and AiAnalysisCard are used by both builds unchanged. They import their data layer as the bare specifier "@data", and each Vite config aliases it to the right implementation. That is the whole seam — when adding a page, import "@data" rather than "../api" and it will work in both targets. Two other swappable pieces follow the same pattern: lib/visionAssets.ts (where MediaPipe loads from) and lib/notify.ts (who shows the OS alert).

MV3 forbids remotely-hosted code. The old CDN URLs would fail the extension CSP and get the listing rejected, so the runtime and the model ship inside the package. The ≈19 MB WASM is copied out of node_modules/@mediapipe/tasks-vision/wasm by a build plugin rather than committed, so upgrading the dependency can never leave a stale runtime behind; the ≈3.7 MB face_landmarker.task is committed under extension/public/models/ because it is not an npm artefact and downloading it at build time would make builds need the network. Verified: loading the panel issues zero external requests, so the extension also works fully offline.

5f.2 Why monitoring lives in the panel

An MV3 service worker has no DOM, so it cannot hold getUserMedia. Capture therefore runs in the panel document, which means closing the side panel ends the session. The obvious alternative — an offscreen document — would move detection back into a permanently hidden context, i.e. straight into the throttling described in §5e. The panel is visible while you browse, so requestAnimationFrame runs at full rate, which is exactly what blink detection needs. The header carries a Tab button for the full-window version.

Chrome will not show a camera prompt inside a side panel. Confirmed in the field: getUserMedia rejects with NotAllowedError and no bubble ever appears, so the generic "tap the lock icon" copy was actively misleading — there is no lock icon to tap. Permission is stored per extension origin, so the fix is to grant once from a normal tab. lib/cameraRecovery.ts is the seam: the extension registers a recovery action (open panel.html?surface=tab#/monitor), the web app registers none, and Monitor renders whatever it gets. It fires pre-emptively too — Monitor queries navigator.permissions.query({name:"camera"}) on mount, so a panel whose state is prompt or denied shows the way out before the user clicks anything. The ?surface=tab marker is what tells a document it is somewhere a prompt can appear; without it the tab would sit there offering to open another tab.

Icons are generated, not hand-drawn — see the generator note in the README history; they are committed under extension/public/icons/. manifest.json is copied into the build by a small plugin because nothing imports it.

6. Running the Project

6.1 First-time setup

npm install                  # root (concurrently)
npm install --prefix server
npm install --prefix client

6.2 Development (recommended for phone testing)

npm run dev
# Desktop:  https://localhost:5173   (accept the self-signed cert warning once)
# Phone:    https://<PC-LAN-IP>:5173 (same Wi-Fi; Vite prints the "Network" URL)
Camera access on phones requires a secure context. That is why the dev server runs HTTPS with a self-signed certificate. On the phone, tap Advanced → Proceed once. Plain http://192.168.x.x will silently block the camera with no permission prompt.

6.3 Production mode (single port)

npm run build --prefix client
$env:NODE_ENV = "production"          # PowerShell (use NODE_ENV=... on macOS/Linux)
npm run start --prefix server
# Open http://localhost:3001
Production mode is plain HTTP, so phone cameras will be blocked on LAN IPs. For real deployment put the app behind genuine HTTPS (host, reverse proxy, or tunnel).

6.4 Useful facts

  • Server port: PORT env (default 3001). Bind address: HOST env (default 0.0.0.0).
  • Reset all history: delete server/data/sessions.json.
  • Windows Firewall must allow inbound TCP 5173 + 3001 for LAN access.
  • First monitoring run needs internet (CDN model download, ~3–4 MB).

8. Suggested Roadmap

  1. Deploy to a Node-capable host (Railway / Render / Fly.io) with real HTTPS — unblocks mobile camera without cert warnings.
  2. Database — accounts are done (§5c); the remaining half is moving sessions.json / users.json onto SQLite (better-sqlite3 or Prisma) so concurrent writes are safe, plus an account-deletion flow.
  3. Calibration step — 3-second "look at the camera" warm-up to lock the EAR baseline before counting.
  4. PWA — manifest + service worker so users can install it and self-host the model for offline.
  5. Smarter insights — the §5b analysis engine covers the server-side aggregate; still open are trend notifications ("your blink rate dropped this week") and calibrating the weights against real dry-eye questionnaires (OSDI/DEQ-5) once there is labelled data.
  6. Session management UI — delete/annotate sessions, export CSV.

9. Quick Orientation for New Developers

  • Start with PIPO_ALLOW_DEV_LOGIN=1 npm run dev — that gets you past the login page without a Google project — then click through onboarding and all five tabs at both a phone and a desktop window width.
  • Read client/src/hooks/useBlinkTracker.ts (detection core) and client/src/pages/Monitor.tsx (session lifecycle + alert logic). Those two files contain ~80% of the product's complexity.
  • The backend is still small — server/index.js is routing and validation only; the substance lives in analysis.js (scoring), auth.js (sign-in) and db.js (storage).
  • Design tokens (colors, radii, shadows, dark mode) and every responsive breakpoint are in client/src/index.css. Reuse .split / .stat-grid / .card-grid / .chart-box rather than adding inline grids.
  • Run npm test after touching the scoring rules — 19 cases cover the factors and the data quirks they guard against.
  • Commit and push every change (§0). The handoff you are reading lives in the repo, so keep it current.
  • All shared types and the blink-rate→status mapping live in client/src/types.ts.
